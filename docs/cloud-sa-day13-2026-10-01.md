## 已掌握觀念（原學習紀錄）

- DBA 誤刪應使用 Automated Backup + PITR，而不是 Multi-AZ Failover
- Manual Snapshot 適合作為 Migration / Schema Change 前的明確 Recovery Point
- Aurora Global Database 偏低 RTO；Cross-Region Backup 成本較低但 Restore 時間較長
- RPO 要以實際資料落後量驗證，而不是只背定義

## 批改錯誤與修正（原學習紀錄）

### 1. System A / B 沒明確寫出方案名稱

System A（RTO 15 min / RPO 1 min）應明確答 Aurora Global Database；System B（RTO 8 hr / RPO 24 hr）可評估 Cross-Region Backup + Disaster-time Restore。

### 2. Region DR 欄位留白

若採本題較嚴格的 RTO 30 min，較合理的是 Aurora Global Database；若成本優先且能接受更長 Restore，才偏 Cross-Region Backup。

### 3. RTO 30 分鐘寫成『30 分鐘後切回原本 Region』

RTO 的目標是 30 分鐘內在可用的 DR Region 恢復完整服務；切回原 Primary Region 屬於後續 Failback。

### 4. RPO 5 分鐘只驗交易時間

交易資料比對是好方法，但還要持續監控 Aurora Global Database 的 replication / RPO lag，並透過 DR 演練證明。

### 5. RTO 驗證只想到 Application 正常與一筆寫入

還要把 DB Promotion、Application、Network、DNS / Endpoint、Secrets / IAM、Health Check、Traffic Switch 與 end-to-end transaction 全部納入計時。

## 核心知識與複習筆記（原學習紀錄）

- HA ≠ Backup。
- Backup ≠ DR。
- RPO = 資料最多可落後多少；Lag 是證據。
- RTO = 災難後多久恢復服務，不是多久切回原 Region。
- RTO 越短，通常需要越多預先部署的 DR 資源。

### 原始教學｜Database DR
- AZ/instance 故障：Multi-AZ；讀取容量：Read Replica；誤刪或邏輯錯誤：PITR；Region 災難：Aurora Global Database 或 Cross-Region Backup。
- RDS PITR 在保留期間依備份與交易日誌恢復，產生新的 DB instance；Manual Snapshot 適合 Migration 前保留明確時間點；跨區備份不是 Hot Standby。
- 銀行 Loan RTO 30 min/RPO 5 min 需檢查資料、網路、IAM、Secrets、KMS、DNS、應用程式與演練。

### Q1｜Recovery Mechanism（原題）
Production RDS：DBA 14:03 誤刪 500 萬筆交易，14:20 發現，Automated Backup 已啟用。請答：最適合的 Recovery Mechanism？為什麼 Multi-AZ Failover 不能解決？Restore 到什麼時間？恢復成原 Production DB 還是新的 DB Instance？

**使用者原答**：Automated Backup + PITR；跨可用區故障切換不能解決資料異動；14:02；新的 DB Instance。

**原批改**：四項正確；PITR 建立新 Instance，不直接覆寫 Production。

### Q2｜Region DR Trade-off（原題）
System A 核心轉帳：RTO 15 min/RPO 1 min；System B 歷史報表：RTO 8 hours/RPO 24 hours。候選：A. Aurora Global Database；B. Cross-Region Backup → 災難時 Restore。分別選擇、說明原因與成本取捨。

**使用者原答**：System A 需要 15 分鐘內快速切換；System B 有 8 小時恢復時間，可慢慢複製；A 成本高、恢復快，B 成本低、恢復慢。**原答未明確填方案名稱。**

**原批改**：A 應明寫 Aurora Global Database，B 應明寫 Cross-Region Backup + disaster-time restore。Aurora 跨區非同步複寫，非計畫性 failover RPO 非保證為零。

### Q3｜Migration 前 Recovery Point（原題）
銀行星期六凌晨進行 RDS Schema Upgrade 與大量 Migration，希望變更前有明確且可長期保存的 Recovery Point。選項：A. Multi-AZ；B. Read Replica；C. Manual Snapshot；D. NAT Gateway。並說明與 Automated Backup/PITR 的差異。

**使用者原答**：C；快照可保存當時狀態備份；一個是長期保留，另一個是異動錯誤回到異動前。

**原批改**：C 正確。Manual Snapshot 是特定時間點、主動建立、可長期保留；Automated Backup/PITR 提供持續性還原窗口。

### 實作｜Loan System DR（原題與原答）
條件：RTO 30 min/RPO 5 min；AZ Failure 自動恢復、DBA 誤刪復原、Region 災難恢復、Migration 前明確 Recovery Point。回答 AZ Failure、Logical/Human Error、Migration 前、Region DR、Aurora Global DB 與 Cross-Region Backup 優缺點、RPO/RTO 驗證及最大 trade-off。

- AZ Failure：**Multi-AZ HA**。
- Logical/Human Error：**Automated Backup + PITR**。
- Migration 前：**Manual Snapshot**。
- Region DR：**原答留白**，但最後 trade-off 選 Aurora Global Database。
- Aurora Global DB：**恢復快、成本高**。
- Cross-Region Backup：**成本低、恢復較慢**。
- RPO 驗證原答：恢復資料最多只能少故障前 5 分鐘交易，按交易時間判斷。
- RTO 驗證原答：確認系統「30 分鐘後有切回原本 Region」，再驗證應用程式與寫入交易。
- 最大取捨原答：選 Aurora Global Database 達成短 RTO，但維護成本高。

**原批改重點**：Region DR 要明寫 Aurora Global Database；RPO 要量測跨區 replication lag 並比對最後成功 commit；**RTO 是從故障到備援環境恢復端到端服務，不是切回原 Region**；切回原 Region 是 Failback。**Day 13 原分數 82/100。**

## 核心知識

| 比較 | AWS ECS + Fargate | Azure Container Apps | GCP Cloud Run Services |
|---|---|---|---|
| 資源概念 | Cluster / Task Definition / Task / Service | App / Revision / Replica | Service / Revision / Instance |
| 擴縮 | Desired Count / Service Auto Scaling | HTTP/事件規則擴縮 | Request/Concurrency/CPU 等自動擴縮 |
| 典型選型 | AWS 既有系統、全天候 Loan API | Azure 生態或事件驅動 API | HTTP 活動 API、平時低流量 |
| 注意 | 跨 AZ 容量、DB 連線、運維 | Scale Rules、最低副本數 | Scale to Zero、Cold Start、Minimum Instances 成本 |

**ECS 基礎**：Cluster 為邏輯分組；Task Definition 定義 Image、CPU、Memory、Port；Task 是執行中的實例；Service 維持 Desired Count；ECR 儲存 Image，ECS 執行/管理容器；Fargate 免管理主機，ECS on EC2 有更多主機控制。

### Q1｜單選

- A. EKS，所有容器都必須使用 Kubernetes
- B. ECS + Fargate，搭配 ALB、Auto Scaling 與高可用設計
- C. GCP Cloud Run，一定比 AWS 便宜且延遲更低
- D. 單一 EC2 執行 Docker，不需編排

使用者：**B**；正解：**B**。理由：優先沿用既有 AWS 整合，減少底層主機管理；仍須依 SLA/成本/維運評估。

### 實作 1｜平台選型

System A：AWS 既有環境、RDS、全天候、低延遲核心 Loan API。System B：GCP 新建、HTTP、平時少流量、活動突增、非正式入帳的試算 API。

使用者：A 選 ECS + Fargate（既有 AWS）；B 選 Cloud Run（依請求調整）。正確。更完整的說明需納入 HA、Cold Start、VPC/DB、監控、成本、團隊能力與合規。

### 實作 2｜Availability & Scaling

問題：System A 如何避免單 AZ 故障造成服務中斷？使用者：Multi-AZ + ECS Service Auto Scaling。

補充設計：ALB 分配至至少兩 AZ 的 Private ECS Tasks，設定健康檢查、最低容量與擴縮策略（CPU、Memory、RequestCountPerTarget）；RDS Multi-AZ，檢查單 AZ 故障時剩餘容量及 DB 連線上限。Multi-AZ 並不自動保證零中斷。

### 實作 3｜Production Recovery

情境：ECS Healthy，部分 Loan Interest Calculation 錯誤，DB 只新增向後相容的 Nullable Column。是否直接 DB Rollback？如何處理已產生交易？

使用者：先縮小影響、查 Log 與參數，不立即還原 DB；對已產生交易，提出以 Log 找時間後將 DB PITR 回到交易前再重跑。

**修正**：不應預設整庫 PITR；它會倒退其他正常交易，造成資料遺失、重複入帳或對帳不一致。先辨識試算/正式入帳/外部副作用，控制受影響交易，確認根因並視情況回復應用版本；保留相容 Nullable Schema；針對受影響流水按銀行授權程序沖正、補正、重算，確保冪等、稽核軌跡與總分戶帳對帳。PITR 適合特定資料庫災難復原場景，也可在隔離環境協助調查，非少量業務錯帳的預設處置。

## 已掌握觀念（原學習紀錄）

- Backup & Restore 適合較寬鬆 RTO / RPO 與成本敏感 workload
- Warm Standby 代表 DR Region 有完整但縮小的 Running Application
- RTO 越短通常需要越多預先部署的資源
- Warm Standby 相較 Active/Active 用較低成本換取較多 Failover / Scale-up 步驟

## 批改錯誤與修正（原學習紀錄）

### 1. Q1 選 C Warm Standby，但理由其實描述 Pilot Light

DR Region 沒有 Running EC2 Application，所以應選 Pilot Light；若把縮小版 Application 先 Running 起來才是 Warm Standby。

### 2. System B 同時回答 Pilot Light / Warm Standby

RTO 30 min / RPO 10 min 兩者都有可能，但題目要求做決策時要選一個並用實測 RTO 證明；若想降低達標風險，Warm Standby 較保守。

### 3. Active/Active 說成『無延遲、直接切到另一台』

Active/Active 是多 Region 本來就在服務流量，不是故障後才切到另一台；RTO/RPO 是 near-zero/potentially zero，不應寫絕對零延遲。

### 4. Q3 問 Data 問題，卻列 Compute/Network/Encryption/DNS

真正的 Data 問題應包含 consistency、同筆資料 concurrent write conflict、transaction ordering、replication lag、conflict resolution。

### 5. DNS / Traffic 只寫 ALB

ALB 是 Regional Service；跨 Region traffic failover 應補 Route 53 Failover、Global Accelerator 或 ARC 等 Global Routing。

### 6. RTO 又寫成切回原 Region

RTO 30 min 應驗證 30 分鐘內在大阪恢復完整服務；切回東京是後續 Failback。

### 7. 與 Active/Active 比較寫『缺點成本非常昂貴』

Warm Standby 的成本雖不低，但相對 Active/Active 通常較低；真正缺點是 RTO 較長，仍要 Scale Up、Failover、驗證。

## 核心知識與複習筆記（原學習紀錄）

- Pilot Light = Core/Data on；Application 未必 Running。
- Warm Standby = Full App Running but scaled down。
- ALB 是 Regional；跨 Region 切流量要 Global Routing。
- Active/Active 最難的常常是 Data consistency / conflict。
- RTO = 恢復服務，不是 Failback。

### 原始教學｜四種 DR Strategy
Backup & Restore：平常主要保留備份、災難後重建；Pilot Light：核心資料與必要元件先運作，應用程式未必運作；Warm Standby：完整應用程式已運作但容量較小；Active/Active：多 Region 平時均服務流量，金融系統須處理 concurrent writes、consistency、transaction ordering。短 RTO 要提前部署 Network、Secrets、IAM、KMS、DNS、Compute、Image 與演練。

### Q1｜Pilot Light vs Warm Standby（原題）
Loan Application Primary：ALB + EC2 x6 + Aurora；DR：Aurora Secondary、Secrets/Config 已準備，**沒有 Running EC2 Application**。選項 A Backup & Restore / B Pilot Light / C Warm Standby / D Active/Active。另問變成 Warm Standby 至少改什麼。

**使用者原答**：C；理由「核心資料和設定都有在運行，但 EC2 Application 沒有在執行」；改成 Warm Standby 需讓縮小版 EC2 Application 運作。

**原批改 12/20**：應選 **B Pilot Light**；使用者文字理由其實描述 Pilot Light，第二段升級為 Warm Standby 的方法正確。

### Q2｜DR Strategy（原題）
System A 歷史報表 RTO 12 hours/RPO 24 hours；System B Loan Approval RTO 30 min/RPO 10 min；System C 即時付款 RTO near zero/RPO near zero。候選 Backup & Restore / Pilot Light / Warm Standby / Active/Active。用 RTO/RPO/Cost 說明。

**使用者原答**：A Backup & Restore（成本低、恢復時間長）；B Pilot Light、Warm Standby（核心已存在或縮小版運作，成本較高）；C Active/Active（無延遲、直接切換，成本很高）。

**原批改 18/20**：A 正確；B 兩者有可能，強迫單選較偏 **Warm Standby**，須演練驗證；C 正確，但 Active/Active 是兩區平常就服務，不是故障後才啟動，亦不保證零延遲。

### Q3｜Active/Active Data Risk（原題）
兩個 Region 都能更新同一帳戶 Balance。有人說「最好，因為 RTO 幾乎 0」。判斷完整否、至少列三個 Data 問題。

**使用者原答**：不完整；Data 同步、Compute、Network、Encryption、DNS/Traffic、Dependencies。

**原批改 8/20**：應聚焦 **Data Consistency、Concurrent Write Conflict、Transaction Ordering、Conflict Resolution、Replication Lag**；Compute/Network 等是 DR Dependencies，不是題目要求的 Multi-Writer Data Risk。

### 實作｜Loan Warm Standby（原題與原答）
需求：Loan System RTO 30 min/RPO 5 min；Region A 全毀、Region B 接手，但成本低於 Active/Active。設計 Strategy、Primary/DR Region、DB/Compute/App/Network/Secrets/IAM/DNS、Failover、RTO/RPO 驗證、與 Active/Active 取捨。

**使用者原答**：Warm Standby；東京 Primary、大阪 DR；Aurora Global Database；東京 EC2 x4、大阪 EC2 x2；兩區 App 啟動；路由/SG、憑證/金鑰預備；DNS/Traffic 答 ALB；Failover 步驟：確認故障→切斷東京寫入→大阪 DB 成 Writer→擴容→確認網路密碼權限→切流量→驗證登入交易；RPO 按交易時間驗證 5 分鐘；RTO 再次寫「30 分鐘後切回原 Region」；與 Active/Active 比較答「快速切換、成本昂貴」；Trade-off 答「降低平常成本，換取故障時較多復原步驟與較長恢復時間」。

**原批改 40/40（架構方向）**：Warm Standby 合理，Write Fencing 思維好；但 ALB 是 Regional，跨區需 Route 53 或 Global Routing；RPO 需最後 Commit 對比與 Replication Lag；RTO 到大阪交易成功為止，不含 Failback；Warm Standby 相對 Active/Active **成本與一致性複雜度較低，但 RTO 較長**。**Day 14 原分數 78/100。**
